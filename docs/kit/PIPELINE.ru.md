# Как Мастер Чиф проверяет работу исполнителя

Пользователь описывает задачу и согласовывает план. Команды ниже выполняет Мастер Чиф; они показаны здесь для понимания и отладки.

## Требования и проверка

До реализации Чиф сохраняет список требований. При приёмке для каждого пункта
указывает место в коде и тест. Например, требование «пустой ID возвращает понятную
ошибку» требует проверки до обращения к хранилищу и отдельного теста с пустым ID.
Обычный успешный сценарий этого не проверяет.

Скрипт проверяет полноту таблицы, результат тестов и границы изменений.
Содержание требований и достаточность тестов оценивает Чиф; автоматическая
проверка таблицы сама по себе не доказывает правильность программы.

### Почему требования записывает скрипт, а не Чиф

Мастер Чиф — тоже языковая модель. Если бы список требований жил только в его
контексте, он мог бы потерять пункт или незаметно переписать список после работы
исполнителя, и приёмка сверяла бы код с уже подогнанным списком. Поэтому
`task_metrics.py` работает как нотариус. При `delegate` он читает
`<work_item>-requirements.json` и записывает список в журнал задачи вместе со
снимком файлов. При `review --result accepted` сверяет `<work_item>-checks.json`
с записанным в журнал списком, а не с текущим файлом: каждое требование должно
встретиться ровно один раз. Позднее изменение файла требований на приёмку не
влияет, а Bug Fixer получает те же требования, что и первая попытка.

Обязанности разделены так: `review_checks()` проверяет форму каждого пункта
(требование, код, тест и `verified: true`), `task_metrics.py` проверяет полноту
покрытия, а правильность кода оценивает Чиф по коду и зелёным тестам.

## Размер задания

Обычное задание — небольшой класс или связанный исходный файл. Его конструктор
и короткие методы реализуются вместе. Большой класс можно разделить по независимым
обязанностям. Точечное исправление может затрагивать одну функцию.

## Попытки исправления

После ошибки кода или лимита выполнения исполнитель передаёт работу Bug Fixer.
У него отдельный запас; обратной передачи слабой модели нет. По умолчанию лимиты
на один модуль: исполнитель — 3, Bug Fixer — 6, вместе — 9 неудачных попыток кода.
В конфигураторе можно изменить каждое значение. Срабатывает первый достигнутый предел.
Это пределы ошибок, а не количество запусков тестов или сообщений модели.

При `429`, сбое API или настройки попытка получает `blocked`: частичный код
сохраняется, запас исправлений не расходуется. После устранения причины Чиф
может создать продолжение той же роли с `--previous <ID>`; само прерывание не
запускает другую модель. Старые события и расход остаются в журнале.

## Что защищает чужие файлы

До вызова исполнителя `delegate` делает снимок содержимого файлов проекта. Сразу после ответа `inspect` сравнивает новый снимок с исходным: видит изменения, удаления и новые файлы. Наличие коммита или отслеживания Git не требуется; `.gitignore` исходные файлы не скрывает.

Разрешён только переданный файл. Если исполнитель изменил тесты или другой исходник, принятие блокируется. Мастер Чиф фиксирует возврат, разбирает посторонние изменения, восстанавливает только их и регистрирует новую попытку. Скрипт сам ничего не удаляет и не откатывает. Снимок inspect нельзя перезаписать. Мастер Чиф делает его до собственных изменений; затем может дописать недостающие тесты, и эти правки записываются отдельно. Менять реализацию проверяемого файла после inspect нельзя: нужна новая попытка. Если после зелёного прогона Мастер Чиф добавил тест или изменил другой файл проекта, скрипт требует запустить тесты снова. Старый результат не подтверждает новую версию файлов.

Снимок пропускает служебные и сгенерированные папки: `.git`, `.metrics`, `__pycache__`, `.venv`, `node_modules`, `target`, `build`, `dist`, `bin`, `obj`. Исходники в этих папках хранить нельзя. Логи, отчёты и таблицы ревью нужно писать в `.metrics/`, чтобы они не выглядели как посторонние изменения. Символические ссылки и junction вне исключённых папок останавливают проверку.

## Какие тесты запускать

Во время реализации Чиф проверяет текущий класс или модуль подходящим фильтром
тестового инструмента. Например, Maven может запускать только GameServiceTest.
Область записывается как `--scope GameService`; сам scope не фильтрует тесты.

Начальный красный прогон до реализации записывается один раз с `--phase baseline`. Он сохраняется в журнале, но не расходует лимит неуспешных рабочих прогонов. Повторить baseline или включить его после начала работы в той же области нельзя. Ошибка сборки, отсутствие результата и тайм-аут по-прежнему учитываются: заглушки не оправдывают сломанное окружение.

Предел 12 относится к неуспешным рабочим прогонам подряд в одной области.
Падения разных модулей не складываются. Полный зелёный прогон сбрасывает эти серии.
Общий предел — 60 запусков тестов до решения пользователя о продолжении.
Менять названия областей ради обхода остановки запрещено.

Перед завершением задачи Мастер Чиф обязательно запускает весь набор без фильтра с `--scope full`. Зелёный тест одного класса не означает, что весь проект готов.

## Как записываются ревью и время

Скрипт сам запускает тесты, читает их результат и записывает счётчик. Но решение «код принят» или «вернуть на доработку» принимает Мастер Чиф; для этого он вызывает review.

Перед каждым вызовом модели Чиф регистрирует задание. Если ревью не записано,
отчёт покажет незавершённую попытку. В режиме `--track-delegations` записать ревью
без зарегистрированного задания нельзя. Скрипт учитывает вызовы через протокол
кита; обход протокола не создаёт запись автоматически.

Время считается между start и finish, включая ожидание. Чиф начинает учёт после
получения настоящего ID сессии, до подготовки окружения. Работа до start задним
числом не добавляется.

## Пример одного задания

Сначала Мастер Чиф начинает учёт всей задачи:

```powershell
kit\python.cmd kit/task_metrics.py start --task game-001 --session <реальный-ID> --track-delegations --title "Крестики-нолики"
```

Пишет `.metrics/game-001/GameService-requirements.json`:

```json
[
  "null проверяется до обращения к карте",
  "неизвестный ID вызывает GameNotFoundException"
]
```

После каркаса и тестов регистрирует задание, затем вызывает executor:

```powershell
kit\python.cmd kit/task_metrics.py delegate --task game-001 --work-item GameService --scope GameService --files src/main/java/example/GameService.java --requirements .metrics/game-001/GameService-requirements.json
```

Сразу после ответа фиксирует изменения, до своих правок и запуска тестов:

```powershell
kit\python.cmd kit/task_metrics.py inspect --task game-001 --work-item GameService
```

Код выхода 1 означает посторонние изменения: нужно записать rework и разобраться с ними. Если границы соблюдены, Мастер Чиф читает код, проверяет требования, добавляет недостающие тесты и запускает их:

```powershell
kit\python.cmd kit/task_metrics.py test --task game-001 --scope GameService --junit-dir target/surefire-reports -- mvn -q -Dtest=GameServiceTest test
```

Сохраняет `.metrics/game-001/GameService-checks.json`. Текст каждого requirement должен совпадать с исходным списком:

```json
[
  {
    "requirement": "null проверяется до обращения к карте",
    "code": "GameService.java:getGame, проверка перед games.get",
    "test": "GameServiceTest.nullIdIsRejected",
    "verified": true
  },
  {
    "requirement": "неизвестный ID вызывает GameNotFoundException",
    "code": "GameService.java:getGame, проверка game == null",
    "test": "GameServiceTest.unknownIdIsRejected",
    "verified": true
  }
]
```

Принимает результат:

```powershell
kit\python.cmd kit/task_metrics.py review --task game-001 --work-item GameService --result accepted --checks .metrics/game-001/GameService-checks.json
```

При ошибке вместо принятия фиксирует `review --result rework`, исправляет спецификацию или возвращает замечания исполнителю. Перед повторным вызовом снова запускает delegate. Когда все модули готовы, запускает полный набор с `--scope full` и только после этого finish.
