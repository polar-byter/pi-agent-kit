# Несколько исполнителей и исправитель ошибок

Статус: реализация; итоговые проверки описаны в руководстве и журнале задачи, 16.10.2026.
Задача учёта: `parallel-executors-bugfix-20261016`.
Понятное введение с картой классов и функций: [руководство](EXECUTION_GUIDE.ru.md).

## Сохраняемые гарантии

- По умолчанию разрешены два исполнителя. Проект без сохранённого числа исполнителей
  получает 2 с прежними моделями; явно сохранённое значение, в том числе 1, не меняется.
  В частном режиме `--standalone` задача идёт последовательно.
- Принятой считается проверенная реализация, а не сообщение исполнителя о готовности.
- Исторические журналы не переписываются. Неизвестные токены и стоимость не заменяются нулями.
- Модели и ключи не подменяются автоматически. Исправитель доступен только после явного выбора пользователя.
- Пауза и отмена блокируют новые поручения, включая исправителя; завершение требует возврата всех исполнителей и полного зелёного прогона.
- Учебные `simple.py`, `simple.html`, заглушки будущих уроков и комментарии пользователя сохраняются.

## Границы модулей

| Компонент | Ответственность |
| --- | --- |
| Политика выполнения | Проверка лимитов, классификация причины остановки, выбор разрешённого следующего действия; без API, окон и записи журнала |
| Настройки моделей | Чтение и запись прежних ролей, отдельной роли `bugFixer` и политики `execution`; секреты остаются в переменных окружения |
| Диспетчер попыток | Слоты, зависимости, изолированная рабочая копия, точная связь attempt → worker → session; запуск и ограниченная остановка только своей сессии |
| Метрики | Неизменяемые факты о попытках, проверках, передаче и объединении; совместимое чтение старых событий |
| Приёмка | Проверка результата в рабочей копии, разрешённых файлов и исходного контракта; последовательное объединение с проверкой базового хеша |
| Дашборд | Несколько исполнителей и текущих функций, отдельный исправитель, детализация расхода без повторного суммирования |
| Промпты | Читаемые Markdown-разделы ролей и отдельное русское руководство; один источник рабочего текста |

## Контракты до параллельного запуска

Чиф сначала изучает язык и соглашения проекта. Фиксирует публичные интерфейсы,
`.h`/`.hpp`, общие типы, API, схему БД, единицы измерения, ошибки, владение памятью
и ограничения потоков там, где это применимо. Нельзя требовать все эти артефакты
от каждого проекта: нужны только применимые контракты.

Каждый work item содержит зависимости, разрешённый файл, требования и тестовый
scope. Изменение общего контракта приостанавливает зависимые работы и требует
новой согласованной ревизии. Несколько исполнителей не пишут в общую рабочую папку.
Реализация использует отдельные plain-копии подготовленного снимка под `.metrics`;
Git worktree не требуется. Неотслеживаемые исходники попадают в снимок, а секретные
файлы `.env*`, `auth.json`, `credentials.json`, файл `.git` и папки `.aws`, `.ssh`,
`.codex`, `.agents` в копию не переносятся. Изменения
пользователя не коммитятся и не перезаписываются при конфликте.

## Конфигурация

Прежние `masterChief` и `executors` сохраняются. Добавляются необязательные
`bugFixer` с теми же правилами источника/API и `execution` с количеством слотов
и конечными лимитами попытки. По умолчанию один исполнитель. Старый сохранённый
выбор без `bugFixer` оставляет исправителя выключенным; новая копия шаблона
использует выбранные пользователем DeepSeek для Чифа/исправителя и MiMo для исполнителей.
Язык формы определяется окружением (EN/RU), ручной выбор имеет приоритет;
неподдерживаемый язык заменяется English.
Витрина OpenRouter может назначить модель и роли Bug Fixer. Каждая API-роль имеет
проверку связи и статус сохранённого ключа, без помещения ключа в JSON или форму.

## Ошибка и зацикливание

Ошибка реализации после проверки Чифом, исчерпание бюджета шагов и подтверждённое
повторение одинаковых действий без изменения результата могут передать работу
выбранному Bug Fixer после первой попытки основного исполнителя.

Исправителю передаются контракт, текущий diff, конкретные замечания и публичный
вывод проверок. Приватные рассуждения не читаются и не передаются. У исправителя
свои конечные лимиты и отдельный запас исправлений: обратной передачи основному исполнителю нет.
Ошибка настройки тестов, API/429, пользовательская пауза или отмена не становятся
дефектом кода и не запускают платную эскалацию.

Техническая защита должна действовать во время вызова. Инструкция «не зацикливайся»
и существующий STOP после тестового прогона не останавливают уже выполняющуюся модель.
Используются проверенный установленным CLI лимит `steps`, ограничение времени
контроллером и публичные события инструментов. Отсутствие свежего progress.json
само по себе не доказывает цикл. Перед заменой исполнителя нужно подтвердить
остановку старой сессии; иначе слот блокируется и сообщается ошибка управления.

Сначала подтверждается готовность отдельного сторожевого процесса, затем
допускается вход модели (`attempt_admission`). Контроллер требует общей службы
Desktop; частная standalone-сессия автоматически не перепривязывается.

### Проверка файловых прав перед запросом к модели

OpenCode различает путь инструмента и **ресурс разрешения** — строку, с которой
сопоставляется правило доступа. В установленной версии Desktop 2.0.29 файл внутри
проекта проверяется по пути относительно каталога сессии, с `/` вместо `\`.
Например, абсолютный аргумент `D:\project\.metrics\task\workspaces\one\app\db.py`
становится ресурсом `.metrics/task/workspaces/one/app/db.py`.

`execution_controller.worker_permissions` формирует правила в этом формате:
чтение своей копии, чтение/запись назначенного исходника и точного файла прогресса.
Общий запрет остаётся первым правилом. Контракты доступны только для чтения;
основные исходники, соседние рабочие копии, shell и вложенные агенты запрещены.
Разрешение `external_directory` не требуется: копия находится внутри проекта.

`ExecutionController.verify_permissions` до запуска сторожа и отправки задания
вызывает настоящий `session.permission.create`: проверяет как разрешённые, так
и запрещённые операции. Это **предварительная проверка**, без генерации моделью.
Несовпадение завершает попытку как `setup_error`, без входа модели и без передачи
Bug Fixer. Успешная проверка прав не заменяет проверку реализации и тесты продукта.

В первом чистом прогоне 16.10.2026 старые абсолютные правила не совпали с
относительными ресурсами: обе MiMo получили отказ и вернули работу без изменений.
Нативная проверка исправления воспроизводит этот отказ и подтверждает точечные
разрешения вместе с запретами. Исторические попытки сохраняются в журнале.

## Учёт и совместимость

Для каждой попытки нужны task ID, work item, attempt ID, worker ID, роль,
родительская попытка исправления, точный session ID, базовая ревизия, разрешённые
файлы и причина завершения. Фактическая модель берётся из публичных метаданных
сессии; выбранная в конфигураторе показывается отдельно.

Расход объединяется по уникальному сообщению `(session ID, message ID)`, а не
по каждому повторному экспорту. Одна сессия попытки не смешивается с другой;
непривязанные сессии показываются отдельно. Тесты привязаны к попытке/ревизии:
полный прогон нельзя автоматически приписывать всем одновременно работающим
исполнителям. Старые события без новых полей остаются читаемыми как legacy,
без выдуманных worker ID и стоимости. Приёмка и объединение — разные состояния.

## Промпты для человека

Рабочие инструкции разделяются на Markdown-разделы: роль, вход, разрешённые
действия, контракт, прогресс, результат и условия остановки. Русское руководство
объясняет назначение каждого раздела и содержит ссылки на рабочие файлы.
HTML-комментарии внутри промпта не считаются скрытыми от модели.
Если пояснение не должно отправляться модели, оно хранится вне рабочего текста.
Нельзя создавать параллельные копии инструкции в JSONC и Markdown без проверки
их происхождения. Способ подключения проверяется установленным OpenCode V2.

## Порядок внедрения и приёмка

1. Чистая политика лимитов/эскалации и тесты граничных значений.
2. Совместимый формат настроек, загрузчик и конфигуратор с третьей ролью.
3. Идентичность попыток/сессий в журнале и расходе; тесты legacy и повторного экспорта.
4. Изоляция, диспетчер и безопасное объединение; два независимых исполнителя,
   конфликт общего файла, смена контракта, грязная рабочая папка, прерывание.
5. Watchdog и передача исправителю; цикл/лимит, 429, ошибка среды, отмена во время передачи.
6. Проекции и дашборд: несколько текущих функций, отдельный расход и общий итог.
7. Читаемые промпты, проверка реально загруженных инструкций, документация.
8. Все завершённые тесты кита; отдельный продуктовый эксперимент с двумя настоящими
   моделями проверяет качество их работы и не подменяется имитацией сервисов в тестах.

Не объявлять этап реализованным только по наличию поля количества или промпта.
Проверка без вызова модели подтверждает конфигурацию, но не работу двух реальных
исполнителей. Оплачиваемый эксперимент выполняется только с выбранными пользователем моделями.
