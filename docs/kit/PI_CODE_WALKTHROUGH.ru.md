# Одна задача от сообщения до принятого файла

Обычный start.cmd теперь открывает [штатный интерфейс Pi](PI_NATIVE_TERMINAL.ru.md).
Описание старого консольного входа относится к явному --headless; общие правила
делегации, приёмки и контроля остаются теми же.

Возьми небольшой исходник с одной незавершённой функцией и проследи, как кит
поручает её реализацию. Ниже описан путь по текущему коду. Это руководство
для чтения, а не отчёт о выполненном сценарии с реальной моделью.

## Сначала различи три идентификатора

| Идентификатор | Что обозначает | Где искать |
| --- | --- | --- |
| `task` | Всю задачу пользователя | Имя папки `.metrics/<task>` и журнал `events.jsonl` |
| `session` | Один разговор Чифа или исполнителя | Реестр `.pi/kit-service/registry.json` и история Pi |
| `attempt` | Одну попытку выполнить поручение | Событие `delegation` и связанные с ним события журнала |

У задачи одна корневая сессия Чифа и дочерние сессии исполнителей.
У одного поручения может быть несколько попыток. Связь попытки с её сессией
записывается отдельно событием `attempt_session`. Поэтому нельзя искать
«последнюю сессию» и считать, что она относится к нужной попытке.

## Шаг 1. Подготовь выбор моделей на бумаге

Открой `kit/pi_configuration.py` и начни с `load_choices(root)`.
На входе — корень проекта. Функция читает значения по умолчанию из `pi-kit.json`
и сохранённый выбор из `.pi/kit-models.json`, затем нормализует роли и лимиты.
На этом этапе разговор с моделью ещё не создаётся.

Следующая функция для чтения — `normalize_model_choice(choice, role)`.
Проследи отдельно ветки `pi`, `api` и `lmstudio`: они требуют разные поля.
У собственного API сохраняются адрес, модель, протокол и имя переменной ключа.
`source="opencode"` отклоняется: совпадение названия не даёт доступа в Pi.

Затем прочитай `prepare_pi_configuration` и `write_prepared_pi_configuration`.
Первая входит в согласованную подготовку через `model_switch.preparation`.
Вторая проверяет подключения и создаёт `.pi/agent/models.json` для Pi
и `.pi/kit-runtime.json` с подготовленными ролями для службы кита.
Выбор пользователя и готовая конфигурация — разные состояния.

Ключ собственного API читается из окружения. Нативный вход Pi хранится
в `.pi/agent/auth.json`. Оба пути исключают запись ключа в выбор ролей.
Изменение выбора после подготовки требует повторной подготовки.

## Шаг 2. Найди создание задачи

Открой `kit/run_pi.py`, функцию `main`.
Она получает аргументы запуска, определяет корень и выбирает действие:
открыть настройки, подключить провайдера, подготовить конфигурацию,
открыть существующую сессию или создать задачу.

Для новой задачи проследи `create_managed_task`.
Она выбирает идентификатор задачи, получает модель Чифа и вызывает
`gateway.call('session.create', ...)` с ролью `build` и без родителя.
Результат — реальный идентификатор корневой сессии.

После этого `TaskMetrics.start` в `kit/task_metrics.py` создаёт журнал
и связывает задачу с этой сессией. Если журнал создать не удалось,
запуск пытается убрать уже созданную сессию. Это защищает от разговора,
который не связан с учётом задачи.

Для `--session` прочитай `find_task_for_session`.
Она требует ровно один журнал с указанной корневой сессией.
Прежний разговор открывается по точной связи; новая задача не подменяет его.

## Шаг 3. Проследи отправку одного сообщения

`submit_user_request` получает текст, задачу и сессию.
Сначала проверяет, можно ли продолжать работу по журналу.
Затем создаёт ID сообщения и добавляет контекст: задача уже заведена,
её идентификатор нужно сохранить, исполнителей запускать через контроллер.

Вызов `gateway.call('session.prompt', ...)` передаёт сообщение службе.
В `kit/runtimes/pi_gateway.py` найди `call` и `_request`:
они отправляют локальный HTTP-запрос с токеном службы.
Потребитель не открывает stdin Pi самостоятельно.

В `kit/runtimes/pi_broker.py` переходи к `dispatch` и `_dispatch`.
`dispatch` удерживает блокировку, выполняет операцию и сохраняет реестр.
Ветка `session.prompt` проверяет ID сообщения, текст и состояние сессии.
Она сохраняет допуск сообщения до обращения к процессу Pi.

Посмотри `admissions`: там различаются `unknown` и `accepted`.
Если подтверждение потеряно, сообщение нельзя автоматически переслать:
оно уже могло попасть в модель. Повтор с другим текстом под тем же ID
также отклоняется. Сначала нужно проверить историю и состояние.

## Шаг 4. Отдели наши операции от протокола Pi

`session.prompt` — имя операции внутри кита, а не команда Pi RPC.
В ветке службы оно превращается в `process.request('prompt', message=text)`.
Другие примеры перевода: прерывание — `abort`, очередь — `clear_queue`,
состояние — `get_state`, смена модели — `set_model`.

В `kit/runtimes/pi_rpc.py` прочитай `PiRpcProcess.request`.
На входе — команда Pi и поля. Функция создаёт ID запроса, регистрирует очередь
ожидания, пишет одну JSON-строку в stdin и ждёт подтверждённый ответ.
Таймаут означает отсутствие подтверждения, а не доказанный отказ выполнить команду.

Рядом `_read_messages` читает stdout процесса.
Ответ с `type="response"` направляется ожидающему запросу по его ID.
Остальные события обновляют наблюдаемое состояние и передаются службе.
Так один читатель обслуживает нескольких потребителей кита.

Особенно посмотри `agent_start` и `agent_settled`.
Первое снимает признак завершения, второе устанавливает его.
Окончание отдельного ответа ещё не заменяет подтверждение завершения работы.
`get_tree` Pi описывает ветви истории разговора во времени.
Наше `gateway.tree` описывает семейство сессий Чифа и исполнителей.
Это разные деревья и разные причины их читать.

## Шаг 5. Перейди от Чифа к одной попытке

В `kit/execution_controller.py` открой `ExecutionController.launch`.
На входе — поручение, исходник, требования, договорённости, зависимости и роль.
Проверки бюджета и зависимостей идут до отправки задания.
Затем создаются копия проекта, запись попытки и дочерняя сессия исполнителя.

Прочитай `verify_permissions` как таблицу ожидаемых разрешений.
Назначенный исходник и прогресс доступны для записи, другие исходники,
shell и вложенные агенты запрещены. `session.permission.create` проверяет
действующие правила до передачи текста модели. Неверное разрешение — ошибка
настройки, а не неудачная реализация и повод тратить попытку исправителя.

После допуска появляется связь `attempt_session` и запись принятия поручения.
Теперь сторож может наблюдать именно эту попытку, с её зафиксированной политикой.

## Шаг 6. Посмотри, как заканчивается исполнение

`observe` читает экспорт сессии, проверяет родителя, считает шаги и повторения,
сопоставляет состояние с лимитами и различает ошибки API и ошибки работы.
Исчезновение вывода само по себе не признаётся циклом или успешным окончанием.
`watch` вызывает наблюдение и принимает решение об остановке.

В `stop` проследи последовательность: прерывание, очистка очереди,
проверка отсутствия активности, затем событие `attempt_end`.
Если остановка не подтверждена, замена исполнителя не разрешается.
На стороне Pi `stop_run` ждёт `agent_settled` и повторно проверяет `get_state`.

Затем перейди в `TaskMetrics.inspect`, `test` и `review`.
Здесь фиксируются изменения, результаты тестов и предложенное Чифом решение.
Одного слова `accepted` недостаточно: общие проверки должны разрешить приёмку.

В `ExecutionController.integrate` посмотри входные проверки.
Нужны принятие именно этой попытки, остановленный исполнитель, неизменившиеся
исходник и договорённости, а также копия, не изменённая после тестов и инспекции.
Только затем исходник переносится и добавляется событие `integration`.

## Шаг 7. Проследи одну кнопку паузы

В `kit/dashboard/controls.py` начни с `TaskControls.request`.
Она проверяет допустимость перехода, вызывает `context`, получает блокировку
операции и сохраняет промежуточное состояние с запретом новой работы.
`context` сверяет журнал и корневую сессию, включая отсутствие второго журнала
с той же корневой сессией. Это защита границ задачи.

`_run` выполняет действие в фоне. Для остановки `stopped_tree` сначала
прерывает координатора, затем детей, перечитывает семейство и проверяет,
что состав стабилен и активных участников нет. Для продолжения проверяются
пауза и ревизия моделей, затем вызывается `gateway.resume`.

Для удаления шлюз работает только с семейством выбранного корня:
сначала проверяет остановку всех потомков, затем удаляет от листьев к корню.
Другие корневые сессии проекта не относятся к этой операции.
После подтверждения удаления сессий контроллер может удалить метрики задачи.

## Шаг 8. Проверь, что означает расход

В `kit/runtimes/pi_exports.py` посмотри `normalize_session_export`.
Она приводит историю Pi к сообщениям и инструментам, которые читает общий кит.
Токены берутся из фактического `usage`. Для собственного API неизвестная цена
остаётся неизвестной: технический ноль в описании провайдера не доказывает,
что запрос бесплатный. Отчёт не должен превращать отсутствие цены в нулевую стоимость.

Теперь повтори чтение для одного события: найди, кто его создаёт, где оно
сохраняется и какая проверка читает его перед следующим действием.
Так можно изучать систему по одному переходу, не удерживая все модули сразу.
