# OpenCode: Мастер Чиф и исполнители

> English version: [README.en.md](../../README.en.md) · Пошаговый старт: [QUICKSTART.ru.md](../../docs/user/QUICKSTART.ru.md) · [Quick start (EN)](../../docs/user/QUICKSTART.en.md) · [Инструкция для новичка](../../docs/user/OPENCODE_KIT.ru.md)

Ты описываешь задачу в OpenCode, а дальше работает команда ИИ-агентов. **Мастер Чиф**
(основной агент `build`) составляет план и договорённости между частями программы,
пишет заготовки и тесты, поручает реализацию **исполнителям**, проверяет их работу
и в конце проверяет интерфейс приложения. Если исполнитель ошибся или упёрся
в лимит, подключается **исправитель ошибок** (Bug Fixer). Все шаги
записываются в журнал, а дашборд в браузере показывает ход работы.

**Это похоже на стройку.** Мастер Чиф — прораб: читает задание, чертит план,
раздаёт работу и принимает результат. Исполнители — рабочие: каждый делает свой
небольшой участок строго по чертежу, и их может быть несколько одновременно.
Исправитель переделывает участок, если он не получился.
Твоя роль — сказать, что нужно, ответить на вопросы и принять результат.

## Как это работает — в восьми схемах

Схемы анимированные; данные в них примерные. Те же схемы с подробными шагами —
в [быстром старте](../../docs/user/QUICKSTART.ru.md).

### 1. Установка за четыре шага

Нужны [OpenCode Desktop](https://opencode.ai/download) и ZIP этого репозитория
(**Code → Download ZIP**). Python 3.13.16 с Tk установщик подготовит автоматически
с официального python.org; при первом запуске нужен интернет. Распакуй архив и дважды щёлкни
**install.cmd**. Мастер установки сам найдёт Desktop, создаст папку проекта, скопирует
туда кит и откроет окно настроек моделей. Там уже стоят бесплатные модели — достаточно
нажать «Сохранить настройки» и «Подготовить OpenCode». Потом проект открывается в Desktop:
скопируй пример задания, вставь в новый чат **build** и отправь. Мастер сам ничего
модели не отправляет.

Для Ubuntu, Debian и Mint доступен [установщик `.deb`](../../docs/user/LINUX_INSTALL.ru.md):
открой пакет мышкой, затем запусти OpenCode Project Setup из меню приложений.

### 2. Кто в команде

У каждого своя роль. Мастер Чиф думает и проверяет. Исполнители пишут код по готовым
описаниям — их может быть от одного до восьми, и каждый работает в своей копии файлов.
Исправитель ошибок получает свой запас попыток, если исполнитель не справился. **Контроллер** — обычная
программа кита (не ИИ): он раздаёт копии файлов, следит за лимитами и переносит принятый код
в проект. Журнал и дашборд делают всё это видимым.

![Кто в команде](../../readme_gif/02_team.gif)

### 3. Как Мастер Чиф готовит работу

Задачу можно написать прямо в чате или в файле `TASK.md` и отправить «Начинай»;
если они расходятся, главнее чат. Мастер Чиф сам читает правила кита (`AGENTS.md`),
план прошлых сессий (`currentsteps.md`) и то, что уже есть в проекте. Решает, из каких
частей будет программа и в каком порядке, и заранее фиксирует договорённости между
частями — какие функции есть, что они принимают и возвращают. Пишет заготовки
с подробным описанием и сразу тесты. Пока функции пустые, тесты не проходят.

![Как Мастер Чиф готовит работу](../../readme_gif/03_plan.gif)

### 4. Несколько исполнителей одновременно

Если две части программы не зависят друг от друга, их можно делать параллельно.
Контроллер даёт каждому исполнителю **свою копию файлов** — основной проект они не
трогают и друг другу не мешают. За каждой попыткой следит сторож: сколько шагов,
сколько времени, не повторяет ли модель одни и те же действия. Мастер Чиф проверяет
каждую копию отдельно — её изменения, её тесты, все требования. Принятые файлы
переносятся в проект по одному, и если файл там успел измениться, ничего не
перезаписывается. В конце — полный набор тестов на основном проекте.
По умолчанию исполнитель один; число меняется в настройках.

![Несколько исполнителей одновременно](../../readme_gif/04_parallel.gif)

### 5. Исправитель ошибок: когда и как

Если проверка нашла ошибку в коде исполнителя или исполнитель исчерпал шаги или время,
работа переходит исправителю: тот же файл, те же требования и текст ошибок
тестов. Он чинит только тела функций, а Мастер Чиф снова проверяет. Ошибка сервиса
(в том числе лимит запросов `429`), сломанная тестовая среда, пауза или отмена
исправителя не запускают — это не ошибки кода. Если запас исправителя или общий предел исчерпан,
работа останавливается со словом `STOP` и ждёт твоего решения; обратно исполнителю
она не уходит.

![Исправитель ошибок](../../readme_gif/05_bugfixer.gif)

Схема показывает одну передачу работы. Если нужны дополнительные исправления,
они остаются у Bug Fixer в пределах настроенного запаса: по умолчанию до 6 неудачных
попыток. У исполнителя предел 3, общий предел — 9 на модуль. Сбои API и настройки
учитываются отдельно. Эти значения можно изменить в окне моделей; они не гарантируют
успеха и защищают от бесконечной работы.

### 6. Финал: интерфейс, тесты, отчёт

Когда все части приняты и перенесены в проект, начинается этап улучшения UI/UX.
Мастер Чиф запускает приложение и проходит обычные сценарии руками: открывает формы,
заполняет, сохраняет, специально вводит ошибку. Отмечает, что мешает пользователю —
бледный текст, кнопку без подписи, непонятное сообщение об ошибке — и правит интерфейс,
не трогая логику. Затем полный набор тестов, итоговый отчёт и файл запуска.

Этап записывается в журнал задачи, и без этой записи кит не даст завершить задачу.
В отчёте и дашборде будет одна из строк: «Этап улучшения UI/UX выполнен: проверено
сценариев — 5, исправлено замечаний — 3», «Этап улучшения UI/UX пропущен ввиду
отсутствия браузера для проверки» или «Этап улучшения UI/UX не требуется: у приложения
нет интерфейса».

![Финал](../../readme_gif/06_final.gif)

### 7. Модели, лимиты и ключи

В окне «Модели проекта» у каждой роли своя модель: из каталога OpenCode, через свой
API или — для исполнителей — локально в LM Studio. Здесь же задаётся, сколько
исполнителей работает одновременно и лимиты одной попытки (шаги, секунды, повторы),
отдельные лимиты исправителя, а исправителя можно и выключить. Каталог OpenRouter
показывает цены и позволяет щелчком подставить модель в роль. Ключ API хранится
в переменной Windows, в проекте — только её имя; «Проверить связь» ничего не генерирует.
Для новой задачи после «Подготовить OpenCode» открой чат build. Текущую задачу сначала приостанови, затем продолжи из дашборда.

![Модели, лимиты и ключи](../../readme_gif/07_models.gif)

### 8. Дашборд: видно каждого исполнителя

Дашборд открывается сам. В блоке «Сейчас в работе» виден каждый участник и функция,
над которой он работает. «Детализация работ» показывает все попытки: кто делал, чем
закончилось, перенесено ли в проект. «Токены» — расход по моделям и по каждой попытке;
если части данных нет, сумма помечается «≥», а ноль не подставляется. Кнопки
приостанавливают, продолжают, останавливают или удаляют задачу целиком — со всеми
исполнителями. Язык интерфейса — русский или английский, по языку браузера, с ручным
переключателем.

## Как пользоваться

Самый простой путь — мастер установки (схема 1) и [инструкция для новичка](../../docs/user/OPENCODE_KIT.ru.md).
Подключить кит к уже существующему проекту вручную помогает [быстрый старт](../../docs/user/QUICKSTART.ru.md).
Установка инструментов делается один раз на компьютер.

ТЗ можно написать прямо в чате или сохранить в `TASK.md` и отправить короткое
«Начинай». Файл необязателен, если задача уже описана в чате. Текущие указания
пользователя имеют приоритет. Правила кита, план и остальные нужные документы
Мастер Чиф читает сам; перечислять их в сообщении не требуется. Например:

> Добавь учёт расходов: сумма, категория и дата. Отрицательную сумму принимать нельзя. Сначала покажи план.

Мастер Чиф предложит решение. Ты обсуждаешь требования и утверждаешь план. После этого он сам распределяет задания, вызывает нужные скрипты и проверяет результат. Если ему не хватает информации или доступа, он объясняет, что нужно от тебя.

Для смены моделей в текущей задаче приостанови её в дашборде, сохрани выбор в настройках, нажми «Подготовить OpenCode» и продолжи задачу. Подробнее — [смена моделей во время работы](../../docs/user/LIVE_MODELS.ru.md). Если исполнители работают через
LM Studio, модель должна быть загружена и её сервер включён; другим источникам это
не нужно. Служебную подготовку выбранных моделей Мастер Чиф выполняет по `AGENTS.md`;
`kit/run_opencode.py` остаётся подготовщиком конфигурации и дополнительным способом запуска.

Параллельная работа исполнителей и сторож лимитов работают в общей службе OpenCode
Desktop. В частном режиме `--standalone` кит работает по прежнему последовательному
протоколу. Старые сохранённые настройки и журналы читаются как раньше.

В дашборде можно приостановить задачу со всеми исполнителями, продолжить,
отменить или удалить её сессии и метрики, сохранив исходники.
Семантика и ограничения: [управление задачами](../../kit/dashboard/CONTROLS.ru.md).
Дашборд и конфигуратор поддерживают **EN/RU**; сообщения агентов остаются в оригинале.

Для повторения нашего опыта из Desktop есть [короткая инструкция](../../docs/history/DESKTOP_EXPERIMENT.ru.md).
Свой API, витрина OpenRouter с ценами, роли и язык описаны в
[руководстве конфигуратора](../../kit/configurator/UX.ru.md).

## Что Мастер Чиф делает по ходу работы

Мастер Чиф разбивает задачу на небольшие части, чтобы локальный исполнитель получал понятное задание. Обычно одно задание — небольшой класс целиком: конструктор и связанные методы. Отдельную функцию отдаём при точечном исправлении или когда класс слишком большой.

1. Читает план проекта и текущий код, уточняет требования.
2. Открывает учёт задачи, чтобы её статистика не смешалась с предыдущей работой. Команда начала учёта автоматически запускает дашборд проекта и открывает страницу этой задачи.
3. Создаёт каркас кода и пишет тесты. Пока функции не реализованы, падение этих тестов ожидаемо.
4. Передаёт исполнителю небольшой класс или связанный файл с заранее записанными требованиями. Если выбрано больше одного исполнителя, независимые части идут параллельно, каждая в своей копии файлов.
5. Проверяет полученный код. Если нужны исправления, записывает возврат; после ошибки кода или лимита попытки передаёт работу исправителю ошибок.
6. Запускает тесты через скрипт учёта и проверяет результаты. Принятые файлы переносит в основной проект по одному.
7. Проверяет интерфейс в реальных сценариях, когда это позволяют инструменты, и правит его отдельным этапом.
8. Запускает полный набор тестов, обновляет план, собирает статистику и показывает итог.


## Что ты получишь в конце

В процессе работы локальный дашборд показывает статус задачи, события, рабочие
прогоны тестов, возвраты на доработку и сбои исполнителя. Страница сама обновляется
каждые 2 секунды; можно выбрать другую задачу этого проекта и открыть итоговый отчёт.
Сервер используется повторно между задачами. Подробности — [дашборд](../../kit/dashboard/README.ru.md).
Дашборд показывает архитектуру, фактические модели, передачу работы исполнителям,
текущую функцию, заявленный и принятый прогресс, детализацию работ и доступные
токены во время задачи. Кнопка Settings открывает конфигуратор моделей проекта.
После завершения видны итог, ссылка на папку и просмотр файла запуска.
Прогресс функций требует опубликованного реестра и сообщений исполнителя;
отсутствующие данные и токены не подменяются нулями.

Мастер Чиф объяснит, что сделано, какие проверки прошли и что осталось нерешённым. Отдельным блоком покажет:

- время задачи;
- токены платных моделей;
- токены бесплатных / локальных моделей — всё, что работает через `lmstudio`;
- токены бесплатных облачных моделей — OpenRouter с окончанием `:free` и OpenCode с окончанием `-free`;
- расход по каждой попытке исполнителя и исправителя — входит в общий итог;
- число возвратов кода на исправление после ревью;
- сколько полных запусков тестов завершилось успешно и как закончился последний запуск.

Токены — единицы текста, который модель получает и генерирует. Они помогают увидеть распределение работы между моделями. Стоимость и процент экономии скрипт пока не рассчитывает.

## Как Мастер Чиф собирает статистику

Мастер Чиф сам вызывает `kit/task_metrics.py` в нужные моменты. Это часть его оркестрации — управления порядком работы и исполнителями. В обычной задаче вводить команды этого скрипта тебе не требуется.

1. **Начало задачи.** Мастер Чиф передаёт скрипту время и ID сессии — текущего разговора в OpenCode. Это отделяет новую задачу от предыдущей работы.
2. **Ревью.** После проверки кода Мастер Чиф записывает, принят он или возвращён на исправление. Один возврат считается одной переделкой, даже если замечаний несколько.
3. **Тесты.** Мастер Чиф запускает их через скрипт. Скрипт сохраняет настоящий результат команды. «3 из 5 успешных прогонов» означает три успешные тестовые команды из пяти. Отдельно указано, сколько прогонов проверяли полный набор, а сколько — выбранный класс или модуль. Пустой набор и пропущенные тесты полным успехом не считаются.
4. **Токены.** Перед итоговым ответом Мастер Чиф поручает скрипту прочитать сообщения основной и дочерних сессий OpenCode. Скрипт выбирает завершённые сообщения за время задачи и складывает их счётчики по моделям.
5. **Группы моделей.** Все модели провайдера `lmstudio` попадают в локальную группу, модели OpenRouter с окончанием `:free` и OpenCode с `-free` — в группу бесплатных облачных, остальные известные провайдеры — в платную по умолчанию. Новые модели LM Studio учитываются без ручного списка.
6. **Отчёт.** Скрипт сохраняет `.metrics/<ID задачи>/report.md`. Мастер Чиф вставляет его в итоговый ответ. Если ответ готовит планировщик, он использует тот же файл.

Если OpenCode не отдаёт данные, отчёт сообщает «нет данных». Время включает ожидание твоих ответов, а токены сообщения после сборки отчёта ещё не учтены. Подробности и команды для отладки находятся в [инструкции по статистике](../../docs/kit/METRICS.ru.md).

## Как продолжить после перерыва

Мастер Чиф ведёт `currentsteps.md`: записывает завершённые шаги, решения и следующие задачи. В новом разговоре можно попросить:

> Прочитай план проекта и продолжи следующую задачу.

Мастер Чиф должен сам найти план по правилу из `AGENTS.md`. По умолчанию файл хранится в выбранном Obsidian Vault, а без Obsidian — в корне проекта.

## Если что-то перестало работать

Начни с описания проблемы Мастер Чифу. Например:

> Локальный исполнитель перестал отвечать. Проверь настройки и связь с LM Studio, покажи причину.

Мастер Чиф может прочитать конфиг, запустить проверку подключения и небольшой пример для локальной модели. Если проблема требует твоего действия — например, загрузить модель в LM Studio, — он объяснит, что сделать. Команды диагностики предназначены для агента и ручной отладки; весь список перед каждой задачей запускать не нужно.

## Версии и обновления

Кит использует CLI установленного OpenCode Desktop. Подробности выбора команды и проверки совместимости приведены ниже.

### Какой OpenCode использует кит

На одном компьютере часто стоит несколько OpenCode: приложение Desktop со своим CLI внутри и отдельно установленные команды, например через npm. Версии у них могут сильно различаться. Старый CLI не понимает настройки, которые пишет кит: он отклоняет ключи `providers` и `agents` или молча оставляет агентам прежние модели.

Все скрипты кита — запуск, `--prepare-only`, окно настройки моделей и статистика — ищут OpenCode в одном порядке (`kit/opencode_cli.py`):

1. Путь или команда из `--opencode`, если ты их указал.
2. CLI внутри OpenCode Desktop: `%LOCALAPPDATA%\Programs\@opencodedesktop\resources\opencode-cli.exe`. Ты работаешь в Desktop, поэтому этот CLI видит те же сессии и совпадает по версии с приложением, которое читает настройки.
3. Команда `opencode` из `PATH` — для Linux, macOS и компьютеров без Desktop.

Обёртки `.cmd`/`.bat` (так npm ставит команды) запуск не использует: они могут исказить аргументы и часто ведут к другой, старой версии. Только статистика берёт такую обёртку как последний вариант: для чтения сессий её хватает.

Как настроить у себя:

1. Проверь, какие OpenCode есть и их версии:

   ```powershell
   Get-Command opencode*
   & "$env:LOCALAPPDATA\Programs\@opencodedesktop\resources\opencode-cli.exe" --version
   ```

2. Если Desktop установлен, кит возьмёт его CLI, даже когда в `PATH` лежит другой `opencode`. Старую команду из `PATH` лучше обновить или удалить, чтобы не запускать её вручную по ошибке. Команды с другим именем (например `opencode2`) кит сам не вызывает.
3. Чтобы использовать конкретный CLI, укажи путь явно: `kit\python.cmd kit/run_opencode.py --opencode "C:\путь\opencode-cli.exe"`, а для статистики — `task_metrics.py finish --opencode ...`.
4. После смены моделей проверь, что OpenCode их принял. `debug agents` для этого недостаточно: он показывает модели агентов, а основная сессия запускается на верхнем ключе `model` конфига. Надёжная проверка — короткая настоящая сессия и модель из её экспорта:

   ```powershell
   $cli = "$env:LOCALAPPDATA\Programs\@opencodedesktop\resources\opencode-cli.exe"
   $out = kit\python.cmd kit/run_opencode.py -- run --format json "Reply with the single word OK." | Out-String
   $session = [regex]::Match($out, '"sessionID":"(ses_[A-Za-z0-9]+)"').Groups[1].Value
   (& $cli session export $session | ConvertFrom-Json).messages.model | Select-Object -Unique providerID, id
   ```

   Там должна стоять модель Мастер Чифа. Модель исполнителей видна в экспорте дочерней сессии после первого задания исполнителю. Если команда пишет об ошибке конфига, значит CLI слишком старый.

После обновления попроси Мастер Чифа проверить совместимость:

> OpenCode обновился. Проверь версию, доступ к сессиям и работу статистики на небольшой задаче.

Мастер Чиф должен проверить доступные команды, выполнить тесты кита и сверить отчёт с экспортом сообщений. Если формат изменился, он покажет, какую часть чтения данных нужно поправить. Новую версию отмечаем как проверенную после такого прогона.

## Где находятся настройки

Эта справка пригодится при первом подключении или если захочешь изменить устройство системы.

| Файл | За что отвечает |
|---|---|
| `opencode.jsonc` | Модели, подключения и права агентов |
| `AGENTS.md` | Порядок работы, команда тестов приложения и расположение плана |
| `.opencode/commands/` | Необязательные шаблоны запросов `/plan-project` и `/module` |
| `kit/` | Скрипты, которые вызывает Мастер Чиф, и их тесты |
| `.metrics/` | Журналы и отчёты задач; в Git не отправляются |

Сейчас `build` использует `opencode-go/deepseek-v4.1-flash`. При запуске через `kit/run_opencode.py` оба исполнителя используют уже загруженный экземпляр LM Studio. Если моделей несколько, скрипт выбирает загруженную модель из настройки `executor` или просит указать ID. Прямой запуск OpenCode без подготовки использует прежние фиксированные алиасы из исходного конфига. Подробности и запуск в уже открытом приложении — в [описании выбора модели](../../docs/user/LOCAL_MODELS.ru.md). Команда `/plan-project` тоже вызывает `build`.

Для другого проекта нужно скопировать файлы кита и указать в `AGENTS.md` его язык, папки и команду тестов. Пошаговое подключение описано в быстром старте. После подготовки можно ставить задачи обычным текстом.

## Подключение своего языка

Кит подходит для любого языка, но скрипт статистики должен **прочитать результат тестов**: сколько их было, сколько упало. Он понимает два формата:

- итоговую строку Python `unittest`;
- **JUnit XML** — общий формат отчётов о тестах. Его читают почти все системы сборки, поэтому инструменты для разных языков умеют его выдавать.

Если результат прочитать нельзя, упавшие тесты всё равно засчитываются как упавшие, но зелёные получают статус «неизвестно», а Мастер Чиф считает прогон проблемой настройки. Поэтому команду тестов в секцию `Project stack` файла `AGENTS.md` нужно записать вместе с флагами отчёта.

| Язык | Что поставить один раз | Команда тестов для `Project stack` |
| --- | --- | --- |
| Python (unittest) | ничего | `kit\python.cmd kit/task_metrics.py test --task <ID> -- kit\python.cmd -m unittest discover -s tests -v` |
| Python (pytest) | `pip install pytest` | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- kit\python.cmd -m pytest --junitxml=.metrics/<ID>/run-NN.xml` |
| Java, Kotlin (Maven) | ничего | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit-dir target/surefire-reports -- mvn -q test` |
| Java, Kotlin (Gradle) | ничего | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit-dir build/test-results/test -- gradlew test` (на macOS и Linux — `./gradlew test`) |
| C# (.NET) | `dotnet add <ТестовыйПроект> package JunitXml.TestLogger` | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- dotnet test --results-directory .metrics/<ID> --logger "junit;LogFileName=run-NN.xml"` |
| JS, TS, React, Vue (Vitest) | ничего | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- npx vitest run --reporter=junit --outputFile=.metrics/<ID>/run-NN.xml` |
| JS, TS, React (Jest) | `npm i -D jest-junit cross-env` | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- npx cross-env JEST_JUNIT_OUTPUT_FILE=.metrics/<ID>/run-NN.xml jest --ci --reporters=default --reporters=jest-junit` |
| Go | `go install gotest.tools/gotestsum@latest` | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- gotestsum --junitfile .metrics/<ID>/run-NN.xml` |
| Rust | `cargo install cargo-nextest` и профиль с `junit` в `.config/nextest.toml` | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit-dir target/nextest -- cargo nextest run` |
| PHP (PHPUnit) | ничего | `kit\python.cmd kit/task_metrics.py test --task <ID> --junit .metrics/<ID>/run-NN.xml -- vendor/bin/phpunit --log-junit .metrics/<ID>/run-NN.xml` |

Правила, которые важно не нарушить:

1. **`--junit <файл>`** — для инструментов, которые пишут один файл. Файла не должно быть до запуска, поэтому Мастер Чиф нумерует прогоны: `run-01.xml`, `run-02.xml` и так далее. В `AGENTS.md` пишется `run-NN`, а номер подставляет Мастер Чиф.
2. **`--junit-dir <папка>`** — для инструментов, которые пишут файл на каждый класс или проект: Maven, Gradle, несколько тестовых проектов .NET (для них в логгере используйте `LogFilePath=<папка>/{assembly}.xml`). Скрипт читает только файлы этого прогона.
3. **Без режима наблюдения.** Jest и Vitest по умолчанию ждут изменений файлов и не завершаются. Нужны `vitest run` и `jest --ci`, иначе прогон закончится по времени.
4. **Windows и `.cmd`.** `npx`, `npm`, `mvn`, `gradlew` скрипт находит сам, дописывать `.cmd` не нужно.

После записи команды проверь её один раз:

```bash
kit\python.cmd kit/task_metrics.py check <те же флаги отчёта> -- <та же команда тестов>
```

`CHECK OK` — можно работать. `CHECK FAILED` — под строкой будут подсказки. Подробно — в `docs/kit/METRICS.ru.md`, раздел 3.

## Как проверяется результат

Перед началом реализации Чиф фиксирует требования. При приёмке связывает каждое требование с кодом и тестом. После объединения модулей запускает полный набор тестов. Зелёная проверка отдельного модуля ещё не означает готовность приложения.

Устройство проверки и команды для отладки — [в справочнике](../../docs/kit/PIPELINE.ru.md).
