# Архитектура задачи «Крестики-нолики»

Задача: `tic-tac-toe-live-20261018`.
Роль: архитектор (Chief). Документ описывает только план; исходный код и тесты
не изменяются. Ведущий прогона сам запускает ExecutionController с двумя
исполнителями, подтверждает остановку, проверяет возвращённые файлы и записывает
приёмку.

## 1. Общая картина

Приложение — локальная игра для двух человек в браузере без внешних библиотек и
CDN. Оно состоит из независимых модулей, которые связывает уже готовый сервер.

```
Браузер  <--HTTP-->  server.py  <--вызовы-->  game_rules.py
                                  \
                                   +-------->  game_page.py
```

`server.py` уже написан и не входит в объём работ. Он вызывает только публичные
функции двух модулей и хранит одно изменяемое состояние игры под блокировкой.

## 2. Поток данных

1. **GET `/`** — сервер под блокировкой читает `self.game_state` и вызывает
   `render_game_page(game_state)`. Результат кодируется в UTF-8 и уходит
   клиенту как полный HTML-документ. Рендер не меняет состояние.
2. **POST `/move`** — сервер читает форму, требует ровно одно поле `cell`,
   переводит его в `int` и вызывает
   `apply_player_move(self.game_state, cell)`. Успешный результат — это **новый**
   словарь состояния, которым сервер заменяет текущий. Ответ — редирект 303 на `/`.
3. **POST `/restart`** — сервер заменяет состояние на
   `create_initial_game_state()` и отвечает редиректом 303 на `/`.
4. **Ошибка** — `ValueError` от правил (или неверная форма) приводит к ответу
   `400 Invalid move`; состояние сервера остаётся прежним.

Ключевая инвариантность потока: функции правил чистые (не мутируют вход), а
сервер атомарно подменяет ссылку на состояние. Страница и движок не знают друг
о друге и не обмениваются объектами, кроме словаря состояния из
`CONTRACTS.md`.

## 3. Общий контракт состояния

Взят из `CONTRACTS.md` и не переопределяется.

```
{
  "board": ["", "", "", "", "", "", "", "", ""],  # 9 элементов: "", "X", "O"
  "current_player": "X",                           # "X" или "O"
  "winner": None,                                  # None, "X" или "O"
  "is_draw": False                                 # bool
}
```

`game_rules.py` и `game_page.py` имеют независимые тела и опираются на этот
контракт. Сервер — единственная точка их соединения.

## 4. Два независимых рабочих элемента

Оба элемента не зависят друг от друга и могут запускаться параллельно. Общий
контракт `CONTRACTS.md` обязателен для каждого.

| # | Рабочий элемент | Файл | Зависимости | Тестовый слой |
|---|-----------------|------|-------------|----------------|
| 1 | `game_rules` | `game_rules.py` | нет | `tests/test_game_rules.py` |
| 2 | `game_page` | `game_page.py` | нет | `tests/test_game_page.py` |

Оба элемента делят один контракт состояния. Пересечений по исходным файлам нет,
поэтому их можно передавать контроллеру одновременно (в пределах сохранённого
числа слотов). `server.py` в работы не входит.

## 5. Полный список функций

### `game_rules.py`

| Функция | Назначение |
|---------|------------|
| `create_initial_game_state()` | Возвращает новое независимое начальное состояние: пустое поле, `current_player="X"`, `winner=None`, `is_draw=False`. |
| `apply_player_move(game_state, cell_index)` | Проверяет ход, копирует состояние, ставит метку текущего игрока, определяет победу/ничью и возвращает новый словарь. Вход не мутирует. |

Внутренние помощники исполнитель может добавлять по своему усмотрению, но они
не расширяют публичный интерфейс. Имена и сигнатуры публичных функций
фиксированы и не меняются.

### `game_page.py`

| Функция | Назначение |
|---------|------------|
| `render_game_page(game_state)` | Возвращает полный HTML-документ UTF-8 с формой `/move` из девяти кнопок, формой `/restart`, статусом на русском, доступными метками, отключением занятых и терминальных клеток. Вход не мутирует. |

Импорт `from html import escape` уже объявлен в заготовке и должен
использоваться для экранирования видимых значений.

### Вне объёма

* `server.py`, `tests/*.py`, `CONTRACTS.md` — не редактируются исполнителями.
* Никаких новых публичных функций, кроме перечисленных.

## 6. Граничные случаи

### Правила (`apply_player_move`)

1. **Тип индекса.** Принимается только `int`, и `bool` отклоняется (`True`/`False`
   — подкласс `int`, но недопустимы). Отклоняются `float`, `str`, `None` и любой
   другой тип — `ValueError`.
2. **Диапазон.** Индексы вне `0..8` (`-1`, `9`) — `ValueError`.
3. **Занятая клетка.** Непустая клетка — `ValueError`.
4. **Завершённая игра.** При `winner is not None` или `is_draw is True` любой ход
   — `ValueError`.
5. **Отсутствие мутаций.** При успехе и при ошибке исходный словарь и его
   `board` не меняются; результат — новый словарь с новым списком `board`
   (`after['board'] is not before['board']`).
6. **Смена игрока.** `current_player` меняется только после законного
   незавершающего хода.
7. **Терминальное состояние.** После победы или ничьей сохраняется игрок,
   сделавший последний ход.
8. **Восемь линий.** Учитываются все линии: три строки, три столбца, две
   диагонали.
9. **Победа на последней клетке.** Если ход закрывает линию и одновременно
   заполняет последнюю свободную клетку — это победа, а не ничья.
10. **Ничья.** Поле заполнено, победителя нет → `is_draw=True`, `winner=None`.
11. **Независимость.** Два вызова `create_initial_game_state()` возвращают
    разные объекты и разные списки `board`.

### Страница (`render_game_page`)

1. **Девять кнопок.** Ровно девять `button` с `name="cell"` и `value` `0..8`.
2. **Формы.** Есть `form method="post" action="/move"` и вторая форма
   `method="post" action="/restart"`.
3. **Отключение.** Занятые клетки и все клетки в терминальном состоянии
   (`winner` или `is_draw`) содержат `disabled`; прочие свободные клетки — нет.
4. **Статус.** Видимый текст содержит одно из: `Ход: X`, `Ход: O`,
   `Победил: X`, `Победил: O`, `Ничья`.
5. **Экранирование.** Значения из состояния, попадающие в разметку,
   экранируются (`escape`); теги `<script>` и `<img ...>` не проходят в ответ.
6. **Иммутабельность.** Рендер не меняет `game_state`.
7. **Локальность.** Никаких `https://`, внешних шрифтов, `src=`-подключений и
   JavaScript.
8. **Доступность и вёрстка.** `lang="ru"`, meta viewport, CSS-сетка
   `grid-template-columns` (три колонки), видимый `:focus`, `aria-label` у каждой
   клетки.
9. **UTF-8.** Документ рассчитан на кодировку UTF-8 (сервер кодирует `.encode('utf-8')`).

## 7. Реестр функций и требования

Для каждого рабочего элемента ведущий сохраняет JSON-список требований в
`.metrics/<task>/<item>-requirements.json` перед запуском исполнителя.
Требования формулируются из `CONTRACTS.md` и разделов 5–6 настоящего документа.
Каждое требование затем проверяется против кода и теста записью
`requirement`, `code`, `test`, `verified=true` в `<item>-checks.json`.

## 8. Стратегия приёмки

1. **Базовая проверка.** Перед реализацией ведущий один раз фиксирует ожидаемый
   красный прогон выбранного слоя (`test_game_rules.py` / `test_game_page.py`).
   Он не считается зелёным.
2. **Запуск.** Для каждого элемента контроллер создаёт изолированную копию и
   одну ограниченную сессию Pi. Оба элемента запускаются независимо.
3. **Остановка.** Перед инспекцией ведущий обязан получить `attempt_end` с
   `stopped=true` для точной попытки; неподтверждённая остановка блокирует и
   инспекцию, и замену.
4. **Инспекция.** Сразу после возврата —
   `task_metrics.py inspect --task <task> --work-item <item>`. Читается полный
   исходник, каждое требование сверяется с кодом и тестом.
5. **Тест попытки.** `task_metrics.py test --task <task> --attempt <attempt>
   --scope <item> -- <тестовая команда>`; тестовая команда сама выбирает нужный
   файл тестов.
6. **Приёмка.** При зелёном тесте и полном соответствии —
   `task_metrics.py review --result accepted` с файлом проверок, затем
   `execution_controller integrate --attempt <attempt>`. Интеграция требует
   неизменности исходного файла, контракта и проверенной копии.
7. **Дефект.** Кодовый дефект возвращается тому же `game_rules` / `game_page`
   через Bug Fixer (`--role bug_fixer --previous <attempt>`) с теми же
   требованиями и контрактом; бюджеты не сбрасываются. Инфраструктурные ошибки
   (API, лимиты, пауза, отмена) сохраняют частичный код как blocked и не тратят
   запас исправлений.
8. **Смена моделей.** Не выполняется архитектором. Любое применение новых
   моделей требует подтверждённой паузы и проверки ревизии.
9. **Завершение.** После успешной интеграции обоих файлов — записанный просмотр
   UI (`ux-review`), затем повторный полный нефильтрованный прогон
   `test --scope full` на интегрированном проекте и только потом `finish`.
   Полный прогон должен охватывать оба тестовых файла и `server.py` как точку
   соединения.

## 9. Ограничения для исполнителей

* Редактируется только назначенный исходный файл и файл прогресса.
* Нельзя менять тесты, сигнатуры, импорты, контракт и план.
* Нет доступа к shell, нельзя создавать вложенных агентов.
* Импорты уровня модуля фиксированы заготовкой.
